# 问答生成端的部署与生成链路

## 1. 背景

`adr/2026-09-11-面向-AI-的检索方案选型.md` §2 的决策是复用既有 NLWeb 与
AI Search 实例。该决策在中文场景下未能成立，原因记录在
`adr/2026-09-14-AI-Search-容量限流调优.md` §6.3：AI Search 的关键词索引经
`trigram` 分词后，纯中文查询的召回仍为 0；NLWeb 的 `/ask` 在检索层有结果时
把含中文的查询过滤为空，该行为位于仓库之外，不可控。

站点构建产物中的 Pagefind 索引中文分词可用。实测同一查询的召回数：

| 查询 | Pagefind（浏览器端） | AI Search 检索接口 |
| --- | --- | --- |
| `持久化` | 4 | 0 |
| `集群部署` | 16 | 0 |

## 2. 决策

**召回在浏览器端由 Pagefind 完成，Worker 只负责生成。**

页面取回 top-K 片段后，连同问题提交给自建 Worker `doc-record-ai-answer`，
由 Workers AI 依据片段作答并以 SSE 返回。该分工同时回应了
`adr/2026-09-14-AI-Search-容量限流调优.md` §7 第 5 项：Pagefind 索引不再需要在
Workers 运行时内解析，绕开了 WASM 与自有索引格式的适配问题。

## 3. 部署路径

### 3.1 Workers Builds 路径未成立

先尝试由 Cloudflare Workers Builds 的 Git 集成部署 —— 该路径由 Cloudflare 侧
持有 GitHub 授权，仓库无需保存部署令牌。两次构建均在安装依赖阶段失败：

```
Detected the following tools from environment: pnpm@10.26.2, nodejs@22.23.2
Installing project dependencies: pnpm install --frozen-lockfile
ERR_PNPM_NO_LOCKFILE  Cannot install with "frozen-lockfile" because pnpm-lock.yaml is absent
```

根因是包管理器与安装目录不在同一层：包管理器按仓库根 `package.json` 的
`packageManager`（`pnpm@10.26.2`）判定，安装命令却执行在 Root directory
（`cloudflare/ai-answer`）内，而该目录没有 pnpm 锁文件。判据是根
`pnpm-lock.yaml` 已入库，若安装在根则不会报 absent。

该路径的修法是增加构建变量 `SKIP_DEPENDENCY_INSTALL=true` 并清空 Build command
（本 Worker 无运行时依赖，由 `npx` 自行拉取 wrangler）。该配置作为备选保留在
`cloudflare/README.md` §5.2。

### 3.2 改为 GitHub Actions 部署

仓库密钥补齐三项权限后，改由 `.github/workflows/deploy-ai-answer.yml` 部署，
工作流为手动触发。所需权限：

- Account > **Workers Scripts** > Edit
- Account > **Account Settings** > Read
- User > **Memberships** > Read

其中 Memberships 位于 User 分组而非 Account 分组，是此前部署失败的直接原因
（日志提示 `Unable to get membership roles`）。

判断权限是否生效，只能依据重新部署是否仍报 `Authentication error [code: 10000]`：
编辑令牌权限不改变令牌值，仓库密钥的 `updated_at` 不会变化，该时间戳不能作为判据。

两条路径争用同一个 Worker 名称，只保留 GitHub Actions 一条，Workers Builds
侧的项目已删除。

## 4. 生成改为非流式

`qwen3-30b-a3b-fp8` 在 `stream: true` 下会吞掉输出中的数字。对照实验：片段写明
「Redis 的默认监听端口为 6379」，问「Redis 默认端口是多少」，流式输出为
`Redis 的默认监听端口为 []。`；同一批片段的正文序号「4.」被输出为「.」，
来源编号 `[1]` 同样退化为 `[]`。

该现象一度归因于提示词并连续调整三轮：

- 增加「必须写出具体数字」的要求，无效；
- 增加「不得输出空的 []」，无效 —— 否定式描述本身会把该模式喂给模型；
- 补充输出示例、并把片段编号前缀改为 `片段 [1]：标题`，无效。

改用 `stream: false` 后，同一查询输出 `Redis 的默认监听端口为 6379 [1]。`，
数字与编号均正确。

**教训**：输出中出现系统性字符缺失时，须先区分「模型未遵循格式」与
「输出通道丢失字符」。判据是在片段中写死一个数字并要求模型复述：复述为空则
问题在输出通道，复述正确则问题在提示词。

代价是失去逐字输出，用户需等待完整答案；答案受 `max_tokens: 800` 约束。
响应仍以 SSE 单事件返回，前端解析方式不变。

## 5. 防护调整

来源校验原为 `origin.startsWith(allowedOrigin)` 的前缀匹配，形如
`https://doc-record.iuin888vip.icu.evil.com` 的同前缀域名会被判为合法。
改为按逗号分隔的来源清单逐项相等比较，并以 Node 直接调用 Worker 的 `fetch()`
覆盖 10 个分支（白名单来源、同前缀域名、无关域名、http 降级来源、多来源清单
内外的各项、通配符、无 Origin、非 JSON 内容类型），全部通过。

## 6. 实测结果

站点构建步骤注入 `PUBLIC_AI_ANSWER_URL` 后，页面 `data-recall` 为 `true`、
`data-endpoint` 指向该 Worker。浏览器实测：输入「持久化」返回
「Redis 的持久化通过 `--appendonly` 参数控制，设置为 `yes` 时开启持久化 [2]。」
并附来源列表。

**中文长句的处理**：Pagefind 对多词要求同时命中同一文档，长句召回曾为 0。
2026-09-16 已通过两步解决——整句无结果时按词分别检索再融合排名；片段改为取
覆盖查询词最多的窗口（生成端只收前 1500 字符，取正文开头会切掉命中位置靠后的
内容）。实测「nsenter 的改动是持久化的吗」返回
「nsenter 的改动是非持久化的，仅在命令执行期间生效，退出后恢复原有上下文 [1]。」
实现细节与实测数据见 `cloudflare/README.md` §5.1.1。
