# 翻译平台由 Crowdin 迁移至 Weblate

## 1. 背景

项目当前使用 Crowdin 作为翻译管理平台，配置见仓库根目录 `crowdin.yml`，配合
`package.json` 中的 `crowdin:sync` 脚本与 GitHub Actions 中的上传/下载步骤运作。

经核查，该链路存在一个结构性问题：

```
git ls-files i18n    # 返回空
```

`i18n/` 目录未被纳入版本控制。CI 中的 Crowdin 上传与下载步骤均以 `|| true` 收尾，
失败不阻断构建。由此产生的后果是：

- 译文仅存在于 Crowdin 云端与 CI 的临时工作区，仓库中不留副本；
- 源文件更新后，译文与源文的一致性无法在本地复现与校验；
- 译文的历史变更不可追溯，也无法回滚；
- 一旦 Crowdin 项目或令牌失效，全部翻译成果随之丢失。

翻译工作流需要满足「仓库为唯一事实来源」这一前提。当前方案不满足。

## 2. 决策

采用 **Weblate** 作为翻译管理平台，理由如下：

1. Weblate 以 Git 仓库为唯一事实来源，译文通过提交（commit）或合并请求（merge request）
   回写仓库，直接消除第 1 节所述的黑盒问题；
2. 提供翻译记忆库（Translation Memory）、术语表（Glossary）、自动建议与质量检查，
   满足跨文档译文一致性的管理需求；
3. 采用 GPL-3.0 许可，自建部署无席位费用、无托管字符串上限；
4. 自 2026.5 起原生支持 MDX，自 2026.7 起支持翻译 YAML front matter 中的指定字段，
   与 Astro Starlight 的内容格式高度契合。

Crowdin 侧既有译文不迁移，直接弃用。依据：该批译文从未进入版本控制，无历史记录、
无校验依据，且其术语体系与后续建立的项目术语表无法保证一致。从空状态重新积累，
配合 Weblate 的翻译记忆库，长期一致性优于承接来源不明的存量译文。

## 3. 方案对比

| 维度 | Crowdin（现状） | Weblate 自建 | Weblate 托管 |
|---|---|---|---|
| 事实来源 | Crowdin 云端 | Git 仓库 | Git 仓库 |
| 译文回写仓库 | 依赖 CI，可静默失败 | 原生支持 | 原生支持 |
| 翻译记忆库 | 支持 | 支持 | 支持 |
| 术语表 | 支持 | 支持 | 支持 |
| 许可 | 商业 SaaS | GPL-3.0 | 商业服务 |
| 费用 | 开源项目免费额度 | 仅服务器成本 | 19 EUR/月起 |
| 托管字符串上限 | 受免费额度约束 | 无上限 | 按套餐 |
| MDX 支持 | 支持（`mdx_v1_2`） | 2026.5 起原生支持 | 同左 |
| front matter 翻译 | 支持 | 2026.7 起支持 | 同左 |
| 运维成本 | 无 | 需自行维护 | 无 |

托管方案亦满足功能需求，且免去运维。若后续自建实例的维护成本超出预期，
可平滑迁移至 Weblate 托管，无需更换工具链。

### 3.1 承载方式：托管优先（2026-09-11 决策）

承载方式确定为 **Hosted Weblate 的 Libre 计划**，自建降为备用方案。

触发原因：Oracle Cloud Always Free 的可用形状与容量存在不确定性，首轮创建实例
选到了低于最低硬件要求的 AMD 微型实例（详见 5.1.1 节）。而本项目的规模
（4 语言约 14,600 托管字符串）仅为 Libre 计划上限的 9%，且已满足公开仓库与
自由软件许可两项资格要求，托管不产生任何成本。

选择托管的实质影响：

- 不再自行维护操作系统、数据库与升级，运维成本归零；
- 项目数受限为 1，本项目的组件划分在第 8 节，不受此限制影响；
- 事实来源仍为 Git 仓库，译文以提交或合并请求回写，与自建方案的工作流一致；
- 若后续需要深度定制（自建插件、私有部署、数据完全自主），可迁回自建，
  第 1 节至第 8 节的配置依然适用。

### 3.2 承载方式对比

| 维度 | Hosted Weblate Libre | Oracle Cloud 自建 |
|---|---|---|
| 费用 | 免费 | 免费，但依赖免费额度存在 |
| 运维 | 无 | 需自行维护系统与升级 |
| 规格 | 160,000 托管字符串、项目数 1 | 无上限 |
| 容量风险 | 无 | ARM 容量不足时需反复重试 |
| 实例回收风险 | 无 | 长期空闲存在回收可能 |
| 数据自主 | 托管于第三方 | 完全自主 |
| 迁移成本 | 作为起点，迁出自建无工具链变更 | 作为起点，迁入托管无工具链变更 |

## 5. 免费部署方案

### 5.1 首选：Oracle Cloud Always Free

| 资源项 | 免费额度 |
|---|---|
| ARM Ampere A1 计算 | 最多 4 核 + 24 GB 内存（可拆为 4 台实例） |
| AMD 计算 | 2 台 1/8 OCPU + 1 GB 内存 |
| 块存储 | 200 GB（2 个卷） |
| 对象存储 | 10 GB 标准 + 10 GB 低频访问 |
| 归档存储 | 10 GB |
| 出网流量 | 10 TB / 月 |
| 负载均衡 | 1 台，10 Mbps |

永久免费，不设到期时间。相较之下，AWS 与 Azure 的免费层均为 12 个月限期。

注意事项：

- 注册需绑定信用卡用于身份验证，在免费额度内不产生费用；
- ARM 架构要求软件具备 aarch64 构建，Weblate 官方 Docker 镜像提供多架构支持；
- 热门区域常出现容量不足，创建实例失败时需更换区域或稍后重试；
- 长期空闲的实例存在被回收的可能，不宜承载不可中断的服务。

#### 5.1.1 形状选择的坑（2026-09-11 实测）

首轮创建实例时选到了 AMD 微型实例（1/8 OCPU + 1 GB 内存），该规格**不能用于运行
Weblate**：官方文档给出的单节点最低要求为 3 GB 内存与 2 核 CPU，1 GB 内存下
PostgreSQL、Valkey 与 Celery 无法共存。

必须满足以下两点：

1. 形状选择 `VM.Standard.A1.Flex`，并确认界面标注 Always Free-eligible；
2. 规格至少 2 OCPU + 8 GB 内存，建议 2 OCPU + 12 GB。

创建时若提示 `Out of host capacity`，按以下顺序尝试：

- 更换可用性域（AD-1 / AD-2 / AD-3）后重试；
- 更换区域，容量分布随区域差异较大；
- 将账户升级为 Pay As You Go。升级本身不产生费用，免费额度仍然有效，
  社区普遍反馈 PAYG 账户获取 ARM 容量的成功率高于纯 Always Free 账户；
- 使用 OCI CLI 循环重试，容量释放多发生在整点前后。

不应改用 AMD 微型实例作为替代，其 1 GB 内存低于最低要求，属于不可用而非「略小」。

### 5.2 备选方案

| 方案 | 说明 |
|---|---|
| Weblate 托管 Libre 计划 | 面向自由软件项目，160,000 托管字符串、项目数 1、组件与译者无限制 |
| 复用既有服务器 | 若已有闲置的 x86 服务器或 NAS，直接部署 Docker Compose 即可，成本最低 |
| 本地运行 + 按需同步 | 开发期在本机运行实例，仅在执行翻译任务时启动，零服务器成本 |
| 本地运行 + Cloudflare Tunnel | 在本机启动时通过隧道临时发布，便于协作校对，无需常驻公网地址 |

#### 5.2.1 托管 Libre 计划的适用性（2026-09-11 复核）

该计划的限制为项目数 1，其余与 160k 套餐一致。本项目的实际情况：

| 项目 | 数值 |
|---|---|
| 4 语言托管字符串估算 | 约 14,600 |
| Libre 计划上限 | 160,000 |
| 项目数 | 1（与限制一致） |
| 仓库可见性 | 公开 |
| 许可证 | MIT |

规模约为上限的 9%，且公开仓库与 MIT 许可已满足申请条件（该条件已于 2026-09-11
通过统一许可证解决，见第 12 节）。托管方案的代价是不再自建、译文经过第三方服务
托管，但事实来源仍为 Git 仓库，与自建版本的工作流一致。

### 5.3 已排除的方案

| 方案 | 排除原因 |
|---|---|
| GCP Always Free `e2-micro` | 0.25 vCPU + 1 GB 内存，低于 Weblate 的 3 GB 最低要求 |
| AWS / Azure 免费层 | 计算资源为 12 个月限期，非永久免费 |
| Cloudflare Containers | 磁盘全部为临时盘，无持久卷，不适合有状态服务 |
| Fly.io / Render / Koyeb 免费档 | 内存配额在 256 MB 至 512 MB 区间，文件系统不保证持久 |

综合来看，永久免费且规格达标的通用计算资源目前仅有 Oracle Cloud 的 ARM 额度。

## 7. 与 Astro Starlight 的契合度

| Weblate 版本 | 相关能力 | 对 Astro 的意义 |
|---|---|---|
| 2026.5 | 原生支持 MDX 文件，保留 import / export / JSX 组件与表达式 | 覆盖 Starlight 的 `.mdx` 内容文件 |
| 2026.5 | 新增翻译文件 CDN | 可直接对外发布译文文件 |
| 2026.7 | 支持翻译 Markdown / MDX 中 YAML front matter 的指定字段 | 覆盖 Starlight 的 `title` / `description` |
| 2026.7 | 支持从 Weblate 注册 GitHub App 连接仓库 | 简化仓库授权配置 |
| 2026.5 | LLM 自动建议自动接收上下文 | 可用于译文初稿生成 |

Weblate 自 2026.5 起改用日历版本号（CalVer），每月中旬发布。当前最新版本为
2026.9（2026-09-08 发布）。

需注意一处行为差异：MDX 格式下，译文文件中的外部修改不会被回导至 Weblate，
该格式的翻译事实来源是 Weblate 而非译文文件。因此仓库侧不应手工编辑译文文件。

## 8. 组件规划

> **目录约定更新（2026-09-11）**：迁移实施采用 root locale 方案，源语言（中文）内容
> 位于 `src/content/docs/` 根目录而非 `src/content/docs/zh-Hans/`，译文位于
> `src/content/docs/<locale>/`（`en`、`ja`、`zh-Hant`）。下表掩码已按此调整，
> 详见《2026-09-11-Astro-Starlight-迁移实施记录》第四节。

建议按目录拆分 Weblate 组件，避免单一组件文件过多。下表以 `en` 为例，其余语言同理：

组件按 `src/content/docs/` 下的一级目录逐个建立。掩码中的 `*` 是 Weblate 的语言占位符，
因此一个组件即可覆盖全部目标语言：

| 组件名 | 源文模板 | 译文掩码 |
| --- | --- | --- |
| Docker | `src/content/docs/docker/**/*.md` | `src/content/docs/*/docker/**/*.md` |
| 素材 | `src/content/docs/materiel/**/*.md` | `src/content/docs/*/materiel/**/*.md` |
| 工具 | `src/content/docs/tools/**/*.md` | `src/content/docs/*/tools/**/*.md` |
| 博客 | `src/content/docs/blog/**/*.md` | `src/content/docs/*/blog/**/*.md` |
| Kubernetes | `src/content/docs/kubernetes/**/*.md` | `src/content/docs/*/kubernetes/**/*.md` |
| 网络 | `src/content/docs/network/**/*.md` | `src/content/docs/*/network/**/*.md` |
| 操作系统 | `src/content/docs/os/**/*.md` | `src/content/docs/*/os/**/*.md` |
| 中间件 | `src/content/docs/middleware/**/*.md` | `src/content/docs/*/middleware/**/*.md` |
| 编程语言 | `src/content/docs/lang/**/*.md` | `src/content/docs/*/lang/**/*.md` |
| AI | `src/content/docs/ai/**/*.md` | `src/content/docs/*/ai/**/*.md` |
| 其余目录 | 对应源目录 | `src/content/docs/*/<目录>/**/*.md` |

完整清单与建立方式见 `scripts/weblate-create-components.sh`。

**语言代码风格必须设为 BCP（连字符）。** 译文目录名由 `astro.config.mjs` 的 `locales` 键决定，
为 `en`、`ja`、`zh-Hant`；Weblate 默认使用 `zh_Hant` 一类的形式，两者不一致时译文会写入错误目录。

界面文案位于 `src/content/i18n/`，文件名使用 Starlight 的语言标记
（`zh-CN.json` 为源语言，`en.json`、`ja.json`、`zh-TW.json` 为译文），
与 Weblate 的语言代码同样不一致，因此不纳入上述自动组件；当前条目较少，由人工维护。

文件格式选择：

- 纯 Markdown 文件使用「Markdown file」格式。当前 `src/content/docs/` 下无 `.mdx`
  文件，因此暂不需要 MDX 组件；后续引入 MDX 时需改用「MDX file」格式并启用
  `mdx_merge_duplicates=True`，以合并重复字符串，避免表格行顺序变动导致译文丢失；
- 在文件格式参数中启用 `markdown_merge_duplicates=True`：Markdown 默认按出现位置
  将每个字符串视为独立单元，表格行顺序变动会导致译文丢失，合并后可避免该问题；
- front matter 默认被提取为整块可翻译单元，需在文件格式参数中启用
  「翻译 front matter 的值」，使 `title`、`description` 作为独立字符串进入翻译；
- Markdown 在 Weblate 中是单语格式，「单语言译文基准文件」与「新译文的模板」
  两项都填源文路径（`src/content/docs/<目录>/**/*.md`），文件掩码填译文路径。

代码围栏内容默认不纳入翻译。需通过 `md-text` 与相关标志控制 Mermaid、KaTeX
等片段的处理方式。

## 9. 实施步骤

1. **创建项目**：在 <https://hosted.weblate.org/hosting/> 建立 `doc-record` 项目，
   源语言为 Chinese (Simplified)，分支 `main`，通过 Weblate GitHub App 完成授权，
   随后申请 Libre 计划。操作步骤见 `weblate/README.md` 第 0 节。
2. **建立组件**：在「用户设置 - API 访问」取得令牌后执行
   `scripts/weblate-create-components.sh`，脚本默认指向 `https://hosted.weblate.org`。
3. **连接仓库**：通过 Weblate GitHub App 或部署密钥连接 `doc-record` 仓库。
4. **创建组件**：执行 `scripts/weblate-create-components.sh` 按第 8 节的清单批量建立，
   随后在实例上确认语言代码风格为 BCP、front matter 翻译字段为 `title` 与 `description`，
   并配置分支与推送策略。
5. **启用插件**：启用「清理过时的字符串」「压缩 Git 提交」「发现未翻译文件」
   等插件。
6. **建立术语表**：为高频技术术语（镜像、容器、挂载、命名空间等）建立条目，
   并导入翻译记忆库。
7. **移除 Crowdin**：删除 `crowdin.yml`、`@crowdin/cli` 依赖、CI 中的上传下载步骤
   与 `crowdin` 相关 npm 脚本。
8. **验证闭环**：提交一处源文修改，确认 Weblate 检测到变更，翻译后译文以提交
   或合并请求形式回到仓库，且变更可追溯。

第 7 步建议在第 8 步验证通过之后执行，避免在译文回写尚未确认可用时失去回退路径。

## 10. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Libre 计划申请未通过 | 需改用自建或付费套餐 | 备选自建路径已备妥，配置无需变更 |
| 托管服务变更条款或停服 | 翻译服务中断 | 事实来源为 Git 仓库，译文已在本地，可迁出自建 |
| 项目数上限为 1 | 无法另建试验项目 | 在正式项目内调整组件，不另建项目 |
| MDX 译文不回导 | 手工编辑译文丢失 | 在贡献指引中明确禁止手工编辑译文文件 |
| 翻译质量不稳定 | 术语不一致 | 启用术语表强制检查与质量检查，设置审校流程 |
| 翻译量集中释放 | 单次提交过大 | 配置按提交合并策略，或采用合并请求模式分批合入 |
