# 跨端方案调研：桌面 Web、移动 H5 与微信小程序

调研日期：2026-09-09
调研对象：`doc-record` 项目（Docusaurus 3.10 技术文档站点）

## 一、结论

本项目为内容型站点，核心资产是 Markdown 文档与导航结构，交互逻辑极少。跨端改造的实质问题只有一个：**如何让微信小程序渲染现存 367 篇 Markdown**。

推荐采用**内容层复用**架构：

- 桌面 Web 与移动 H5 继续由 Docusaurus 输出，不做框架迁移；
- 微信小程序作为独立工程新增，通过构建期预编译消费同一份 Markdown 源文件。

不建议采用 Taro / uni-app 整体重写现有站点。该路线会丢失 Docusaurus 已具备的静态生成、搜索、国际化与版本管理能力，且重写成本显著高于新增小程序端的成本。

**关键约束：若小程序主体为个人，微信官方明确禁用 `web-view` 组件，H5 套壳方案不可用，小程序端必须原生渲染。**

## 二、现状基线

| 指标 | 实测值 | 说明 |
| --- | --- | --- |
| Markdown 文档数 | 367 篇（`docs/` 353 篇 + `blog/` 14 篇） | `.md` / `.mdx` |
| 正文纯文本体积 | 0.63 MB | 平均单篇 1.8 KB |
| 图片资源 | 52 张，5.75 MB | `png` / `jpg` / `webp` 等 |
| `docs/` 目录总占用 | 105 MB | 含 `tgz`、`tar.gz`、`mobi`、`epub` 等二进制资料，与文档内容无关 |
| 含 Mermaid 图表 | 2 篇 | 占比 0.5% |
| 含数学公式 | 14 篇 | 占比 3.8% |
| 自定义 React 组件 | 4 个（`AISearchNavbar`、`SearchBar`、`sidebarGenerator`、CSS） | 无业务级交互组件 |

结论性判断：

1. 内容以纯 Markdown 为主，未使用 admonition 指令与内联 HTML，跨端渲染的兼容负担很低；
2. 正文体积远低于小程序包体限制，具备全量离线打包的条件；
3. `docs/` 中混入的约 99 MB 二进制资源不应进入小程序包，需在构建脚本中显式排除。

## 三、约束条件

### 3.1 平台侧硬约束

| 约束项 | 官方口径 | 影响 |
| --- | --- | --- |
| `web-view` 主体限制 | 微信官方文档载明「承载网页的容器……**个人类型的小程序暂不支持使用**」 | 个人主体无法内嵌 H5，套壳方案排除 |
| 业务域名 | 需 ICP 备案 + HTTPS + 根目录校验文件 | 个人主体无配置权限 |
| 主包体积 | 单个分包 / 主包不超过 2 MB | 主包仅能放导航树与运行时 |
| 总包体积 | 全部分包合计不超过 30 MB | 正文 0.63 MB，余量充足 |
| 个人主体类目 | 以工具类为主（信息查询、计算类、备忘录等） | 技术文档需归入工具类下适配类目 |

### 3.2 项目侧约束

- 现有站点已启用四语言国际化（`zh-Hans`、`en`、`zh-Hant`、`ja`）并接入 Crowdin；
- 已集成本地搜索、Mermaid、KaTeX，构建链路依赖 `remark` / `rehype` 插件；
- 技术栈为 React 19 + TypeScript + pnpm。

## 四、候选方案对比

### 方案 A：内容层复用（推荐）

Markdown 作为单一事实来源，三端各自渲染，Web 侧零改动。

| 维度 | 评估 |
| --- | --- |
| 现有站点风险 | 无，Docusaurus 保持原状 |
| SEO / 国际化 / 搜索 | 完整保留 |
| 新增工作量 | 小程序端工程 + 构建期预编译脚本 |
| 内容一致性 | 单一来源，构建期保障 |
| 代价 | 需维护两套 UI 代码 |

### 方案 B：Taro / uni-app 整体重写

以跨端框架替换 Docusaurus，一套代码编译 H5 与小程序。

| 维度 | 评估 |
| --- | --- |
| SEO | 显著受损。Taro H5 为单页应用，需额外接入 `prerender-spa-plugin` 或 `tarojs-plugin-platform-nextjs` 才能恢复预渲染 |
| 国际化 | 需自行实现，现有 Crowdin 链路无法复用 |
| 文档能力 | 侧边栏生成、版本管理、本地搜索、Mermaid、KaTeX 均需重建 |
| 适用判断 | 仅当交互逻辑复杂、且需同时覆盖多个小程序平台时收益为正 |

对于以静态内容为主的文档站，该方案的重写成本高于收益。

### 方案 C：`web-view` 套壳

小程序内嵌现有 H5 站点。

个人主体直接排除。若为企业主体，该方案改动量最小，但存在首屏依赖网络、无法离线、受业务域名配置约束等问题。

### 方案 D：移动端独立站点（`m.` 域名）

为移动 H5 单独建站。

对文档站不适用：内容重复导致 SEO 权重分散，且需维护两套内容源。Docusaurus 默认响应式已覆盖桌面与移动，如需增强移动端体验，应在同一套代码内通过媒体查询与条件渲染实现。

## 五、推荐架构

```
docs/（Markdown 单一事实来源）
  ├── Docusaurus 构建 → 桌面 Web + 移动 H5（响应式，静态生成）
  └── 预编译脚本 → 节点树 JSON → 微信小程序分包
```

### 5.1 小程序端技术选型

分两种情形：

**仅覆盖微信小程序时，建议原生小程序 + Skyline。**

理由：所需页面仅 4 至 5 个（目录树、文档详情、搜索、关于），交互极简。Taro / uni-app 的核心价值在于「一套代码编译多个小程序平台」，在单端场景下该价值不成立，反而引入运行时开销。Skyline 渲染引擎在长列表与滚动场景下相较 WebView 有明显性能优势，且官方已推荐新项目采用。

**若后续需扩展至支付宝、抖音等平台，建议 Taro 4.x。**

理由：Taro 采用 React 语法，与现有 React 19 + TypeScript 技术栈一致，无语法迁移成本。uni-app 为 Vue 技术栈，需切换开发范式，且与 HBuilderX 存在工具链绑定。

### 5.2 Markdown 渲染方案

小程序端不宜在运行时解析 Markdown，应在构建期完成转换。现有运行时解析库的定位与本项目场景对照如下：

| 方案 | 特点 | 适配判断 |
| --- | --- | --- |
| `towxml` | 支持 Markdown 与 HTML，支持代码高亮、目录、锚点 | 成熟稳定，扩展需 fork 源码 |
| `mp-html` | 插件机制完善，支持自定义渲染器，性能与安全性较好 | 适合富文本，学习成本较高 |
| `@ant-design/x-markdown-mini` | 去除 HTML 中间层，长文转换性能领先，面向流式输出 | 优势集中在 AI 流式场景，本项目为静态长文，受益有限 |

推荐做法：在 CI 阶段使用 `markdown-it` 或 `remark` 将 Markdown 编译为小程序节点树 JSON，运行时仅做数据绑定，不执行解析。该方式可消除运行时解析开销，同时规避小程序 `setData` 数据量过大的风险。

### 5.3 资源处理

| 资源类型 | 处理方式 |
| --- | --- |
| 正文文本（0.63 MB） | 按目录拆分为分包，支持离线读取 |
| 图片（5.75 MB，52 张） | 托管至 CDN，小程序端远程加载，不进包 |
| 二进制资料（约 99 MB） | 构建脚本显式排除，不进入小程序端 |
| Mermaid（2 篇） | 构建期渲染为图片，或小程序端做降级提示 |
| 数学公式（14 篇） | 构建期由 KaTeX 转为 HTML 片段并内联样式 |

### 5.4 国际化

四语言全量打包约为 2.5 MB，超过主包 2 MB 限制。建议主包仅包含默认语言与导航索引，其余语言置于分包按需加载；或小程序端首期仅上线 `zh-Hans`，待验证后再扩展。

## 六、实施路径

| 阶段 | 事项 | 产出 |
| --- | --- | --- |
| 一 | 确认小程序主体类型与可选类目 | 明确 `web-view` 可用性 |
| 二 | 编写构建期预编译脚本（Markdown → 节点树 JSON） | 可复用的内容管道 |
| 三 | 搭建小程序端骨架：目录树、详情页、搜索、关于 | 可运行的小程序工程 |
| 四 | 处理图片、Mermaid、公式的降级与远端化 | 内容完整性达标 |
| 五 | 接入 CI，与 Docusaurus 构建并行产出 | 内容同步更新机制 |

## 七、风险清单

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 类目审核 | 个人主体可选类目有限，技术文档需匹配工具类下适配子类目 | 提交前核对《个人主体开放服务类目》 |
| Skyline 兼容性 | Skyline 对部分组件支持度与 WebView 存在差异，`rich-text` 表现需实测 | 按页面粒度启用，保留回退至 WebView 的能力 |
| 内容同步 | 两端构建链路独立，存在内容版本不一致的可能 | 以文档 Git 提交为唯一触发源，CI 统一调度 |
| 图片外链 | 远程图片加载受域名与证书策略影响 | 统一托管至已备案域名的 CDN |

## 八、待确认事项

1. 小程序主体类型：个人或企业。该项决定 `web-view` 是否可用，进而决定整体路线；
2. 覆盖范围：是否仅需微信小程序，或后续需扩展至支付宝、抖音等平台；
3. 小程序端是否需要覆盖全部四语言，或首期仅上线中文；
4. 域名 `doc-record.iuin888vip.icu` 是否已完成 ICP 备案并支持 HTTPS。
